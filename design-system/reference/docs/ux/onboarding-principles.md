1. Design for user success, not feature exposure. Onboarding is never a tour of the interface. Restory does not ship guided tours, coach marks, or tooltips that point at buttons. Every surface guides the writer toward the work itself: pick a workspace, arrange sections, edit a section, ask the assistant to revise it. The assistant page demonstrates this stance directly — "no bubbles, provenance first, preview as prose" — assistant turns read like draft prose, not chat decoration.

2. Content can't fix a broken product. If the interface needs a paragraph of instructions, the interface is wrong. Restory follows this by giving each surface a single job: the workspace picker picks a workspace, the graph arranges sections, the editor edits one section, the preview reads the assembled draft. When something cannot proceed, the system explains why in one short sentence ("Open the target section before applying", "Reconnect the workspace before applying") instead of layering tutorial copy on top of a confusing control.

3. Progressive disclosure over information dumping. Expose only what is immediately relevant. The slash-command combobox is the concrete pattern: typing "/" reveals available skills (`/rearrange`, `/tighten`, `/summarise-section`) with descriptions and a single `Enter` affordance for the top match. Skills are not advertised in chrome, banners, or first-run tours; the writer discovers them by reaching for them. Keyboard hints follow the same rule — `Enter send · Shift+Enter newline` appears inside the composer, not as a global help overlay.

4. Minimize effort to the first meaningful moment. Restory makes a deliberate choice here: the first decision is *not* deferred. The workspace picker is the first-run surface, and it forces a single choice ("pick one row or choose a folder") because every other surface depends on it. What is minimized is the *cost* of that choice — remembered workspaces appear as full-row buttons that open on click, with no confirmation step and no persistent selected state. There is no account creation, no configuration wizard, and no profile setup; the path from launch to editing is one click when a workspace is remembered, or one folder pick when it is not.

5. Reduce anxiety around high-stakes actions. Editorial changes are visible and consequential, so the assistant never writes directly to the draft. Proposal cards preview the whole change before it is applied: the proposed prose renders as document content (not a plus-minus diff), the current passage is available under a `Show current opening` disclosure, and the `Apply` button is disabled with a one-sentence reason when the change cannot safely land. Destructive or blocked states are explained in place ("Save results.md before applying"); the writer never has to guess what will happen.

6. Design for a single writer, not for groups. Restory is a desktop tool that opens a folder on the local filesystem. There are no roles, no permissions, no invitations, and no admin-only steps to wait on. This principle from the broader onboarding literature does not apply, and the design system intentionally has no surfaces for it. If group editing ever enters the product, this principle should be rewritten rather than retrofitted.

7. Two unified layers, not three. The book's "UI pattern, content, communication" split assumes a SaaS context with email and in-app messaging. Restory has two: the **UI layer** (empty states, inline status blocks, banners, toasts, the `StatusSurface` primitive, proposal cards) and the **assistant layer** (transcript turns, slash-commands, proposals). There is no email channel, no notification center, and no separate "messaging" team. Anything the product needs to say in context is said by the surface that owns the moment, or by the assistant transcript when the work itself is editorial.

8. Empty states orient, they do not entertain. A blank screen is intimidating, but Restory deliberately does *not* prefill the workspace with sample content. The actual empty-state pattern is: a clear title naming what is missing ("No workspaces on this server", "No workspaces yet", "No sections match your filters"), a one-sentence description that names the next step, and exactly one action (`Choose folder`, `Clear filters`, `View setup guide`). The `StatusSurface` primitive enforces this: title is a noun phrase of six words or fewer, description is one sentence, empty and not-found states require one action, loading forbids it, error is optional. Sample-content empty states are an explicit non-goal — Restory works with the writer's real files from the first session.

9. Onboarding is continuous, delivered in context. Restory does not run a setup wizard and then declare onboarding "done." Discovery happens through three durable affordances: inline status blocks that explain what just changed, the banner pattern for workspace-wide context ("You are editing a draft workspace"), and the assistant transcript itself, where the writer asks for new behavior and the system responds. New skills appear in the slash-command list when they exist; they are not announced through "what's new" modals or timed prompts.

10. Do not branch the first run by intent. The broader literature recommends asking the user upfront what job they are hiring the product for, then customizing the path. Restory rejects this: the workspace picker is "a short, single-purpose list" and explicitly avoids asking who the writer is or what they intend to do. The Job-to-be-Done is already known — open a writing workspace and work on it — and branching the first surface would slow down the only path that matters. Customization happens later, through the choice of skill in the assistant, not through onboarding interrogation.

11. Build the onboarding *primitives* as a design system, not the onboarding *journey*. There is no "levels and steps" skill tree. Instead, the system ships a small set of reusable primitives that every surface composes: `StatusSurface` for loading/error/empty/not-found, `StatusCallout` for inline guidance, the proposal card for any assistant-initiated change, the slash-command combobox for skill discovery, and the picker shell for any single-purpose choice. Consistency across surfaces — same primitives, same copy rules, same focus treatment — is what makes the product feel learnable, not a scripted journey.

12. Prefer high-impact redesign of the *primitive* over low-impact tuning of the surface. When a surface feels wrong, change the primitive that backs it rather than tweaking copy on a single page. The `StatusSurface` consolidation is the model: four states that previously lived as ad-hoc layouts now share one component, one set of copy rules, and one role/aria contract. Button-color optimizations and per-page polish are deferred; primitive consolidation is the work that compounds.
