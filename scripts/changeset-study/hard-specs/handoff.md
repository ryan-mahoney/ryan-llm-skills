### Decisions

- D1. Where does the new code live? In the new `dependency-handoff.mjs`; runtime.mjs re-exports `buildDependencyHandoff`. Reason: runtime.mjs is about 1,400 lines after step 6 (its fix F2 moved wave lifecycle code out), and the live owner rule splits files past about 1,000 lines. A re-export still satisfies "export buildDependencyHandoff from runtime.mjs", and keeping the new module free of runtime.mjs imports avoids an import cycle.
- D2. Public signature? `buildDependencyHandoff({ packageDir, step, targets })` → handoff object or `null`. `step` is the integer step number; `targets` is every package target id. Reason: a pure function of package files can be called directly from tests and the prompt.
- D3. Graph source and fallback? Read `<packageDir>/spec-steps.json`. If the file is absent, or `validateStepIndex(index, { targets }).legacy` is true, return `null`, and the caller keeps today's `currentHandoff` unchanged. Unparseable JSON throws code `dependency-index-unreadable`. `ok:false` throws `dependency-graph-invalid` with the first three `errors`. A step missing from the index, or a non-numeric card name, throws `dependency-step-unknown`. Each refusal is an `Error` with message `${code}: ${message} ${remedy}` and the properties `code` and `remedy`, matching runtime.mjs `refusalError`. Reason: AC-4 keeps legacy packages unchanged; invalid declarations fail closed, and `Runtime.start` already turns a prompt-construction throw into a failed terminal run.
- D4. Returned shape? `{ step, source: 'spec-steps.json requires', index, details, omitted_details, coverage_gaps, obligations }`. Each `index` entry is `{ step, status, reason, wave_id, accepted_commit, review_status, unresolved_obligations, artifacts, artifacts_omitted }`, listed in ascending `requires` order with every dependency included and the list never truncated. Each `details` entry is `{ step, decisions, unresolved, remaining_work, findings, truncated }`. Reason: the compact tuple from Architecture E, with excerpts kept separate so only excerpts are budgeted.
- D5. Status classifier (this step owns it). Scan `runtime/waves/` for names matching `/^[A-Za-z0-9_-]{1,128}\.json$/`; `wave_id` is the basename. A record is readable if its JSON parses and its `version` or `schema_version` equals 1. Valid member phases are queued, provisioning, implementing, reviewing, fixing, confirming, sealed, blocked and cancelled. Valid wave states are open, running, ready-to-integrate, integrating, verifying, promoting, integrated, blocked and cancelled. A record names step N when `members[String(N)]` exists. Each record that names N classifies it per row:

  | Row (first match wins, top to bottom) | status | reason |
  |---|---|---|
  | phase or state outside the valid sets; sealed with `sealed_head` not matching `/^[0-9a-f]{40}([0-9a-f]{24})?$/`; or sealed with `review_artifacts` not a nonempty array of package-relative strings (no leading `/`, no `..` segment) | unknown | `wave-member-malformed:<id>` |
  | phase blocked or cancelled | blocked | `member-<phase>:<id>` |
  | wave state blocked or cancelled | blocked | `wave-<state>:<id>` |
  | phase sealed, wave state integrated | accepted | null |
  | phase sealed, any other wave state | pending | `wave-not-integrated:<id>:<state>` |
  | phase queued, provisioning, implementing, reviewing, fixing or confirming | pending | `member-<phase>:<id>` |

  Combine records in this precedence: any malformed → unknown. Two or more accepted with different heads, or any accepted plus any pending → `conflict`, reason `conflicting-wave-records:<sorted ids joined by ,>`. Otherwise any accepted → accepted (first id in sort order); otherwise any pending → pending; otherwise any blocked → blocked; otherwise unknown with `no-accepted-wave-record`. Finally, if any record file is unreadable, every step that would be `accepted` becomes unknown with `wave-record-unreadable:<file>` (first in sort order), and each unreadable file adds a coverage gap. Reason: Architecture B makes the wave record the sole acceptance authority, and missing or corrupt records must be unknown or blocked. A worker receipt or completion outcome never sets `accepted`.
- D6. Other tuple fields? `accepted_commit` is `sealed_head` only when the status is accepted, and null otherwise. `review_status` is `closed` when accepted, `open` when any record names the step, and `none` otherwise. Reason: the status/reason pair carries the detail; these fields must not suggest acceptance.
- D7. Which completion feeds counts and details? If the step is accepted, use the accepted member's `implementation_run_id ?? run_id` completion (step 10 keeps `implementation_run_id` because `run_id` moves to stage runs). Otherwise use the latest `observedRuns` entry for that step's card (`basename(run.step)` equals `step-NNN-subspec.md`, compared by `started_at`), read from `runtime/runs/<run_id>-completion.json`. `unresolved_obligations` is `gaps.length + learning.remaining_work.length`, counting the full arrays. With no readable completion it is `null`, and a coverage gap `step N: no completion receipt` is added. Review findings join the count in step 8, when fix receipts exist. Reason: this preserves the count even when details are omitted, without inventing step 8's receipt.
- D8. Artifacts? Package-relative, in this order: `runtime/waves/<id>.json` for each record naming the step; the `review_artifacts` of the accepted member, or else of the first record in sort order naming the step, as recorded when it is an array of valid package-relative strings; then, when the file exists, `runtime/runs/<run_id>-completion.json`, `runtime/runs/<run_id>-learning.md` and `learnings/step-NNN-learning.md`; then existing `reviews/step-NNN-*.md`, sorted. Keep the first 8 and set `artifacts_omitted` to the remainder. Reason: portable paths resolved against the prompt's `PACKAGE` line, and serial packages still get review pointers.
- D9. Detail budget? Each list holds at most 4 items, each cut to 300 characters; `truncated` is true when any item or list was cut. Add details in ascending step order while `JSON.stringify(details).length` stays at or below `DETAIL_BUDGET = 8000`. At the first entry that does not fit, that entry and every later one go to `omitted_details`. Keep at most 8 coverage gaps, each cut to 300 characters. `obligations` is exactly: "Paths are relative to PACKAGE. Every listed step is a required prerequisite. Only status accepted means sealed, independently reviewed and integrated; a completed worker receipt is not acceptance. Before editing code that depends on a step in omitted_details or whose status is not accepted, read its artifacts. Omitted details are not evidence of no blockers." Reason: the budget matches today's 10,000-character CURRENT bound minus the index; deterministic order makes the omissions testable, and the index already exposes every status.
- D10. Prompt composition? `dependencyContext(record, targetIds)` builds the handoff with `step` parsed from `basename(record.step)` and `targets = targetIds ?? [record.target]`. If the handoff is `null`, it returns `currentHandoff(record)`. Otherwise it returns `` `DEPENDENCIES: ${JSON.stringify(handoff)}\n` + currentHandoff(record, { sameStepOnly: true }) ``. Reason: same-step observations carry retry state (remaining work, checkpoint reason, dirty revision) without recency inference. `target_ids` comes from `resolveInput` because `other_targets` omits targets that have no worktree.
- D11. Editor outcome receipt? After each launched `runEditor` result, immediately before the existing `editor_finished` event, write `runtime/runs/<id>-editor-outcome.json` atomically as `{ version: 1, session, state, stop_reason, error, full_result_path, recorded_at }`. `state` is `incomplete` when `result.error` is set or `result.stop_reason === 'length'`, and `completed` otherwise. `error` is cut to 300 characters; missing values are `null`. Calls that throw, or that return early from the configuration latch, write nothing. `<id>-editor-sessions.json` keeps its array shape. Reason: a separate receipt preserves the existing session-receipt contract and its test.
- D12. Continuation block? Before launching, if the outcome receipt has state `incomplete`, read the current dirty state with the runtime.mjs `git` helper: `status --porcelain=v1 -z --untracked-files=all`, skipping the source entry that follows each R or C record. On a git error, use `null` for both fields. Keep them; do not redo or revert completed edits. Complete only the remaining obligation in this packet.\n` ``. `dirty_paths` holds at most 50 entries. Never copy the earlier packet or its transcript. Reason: Architecture E requires current dirty state and previous failure without transcript history; the owner's packet supplies the remaining obligation.

Only a later editor packet that completes clears it. Checkpoint, decision-required and needs-spec-correction outcomes pass. Reason: a length stop cannot complete the step, partial work stays recoverable, and the guard runs first so its refusal is attributable.
